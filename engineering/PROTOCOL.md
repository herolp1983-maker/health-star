# Shared engineering contract

Current policy: the user's 2026-10-20 request supersedes manual merging. Read [AUTONOMOUS.md](AUTONOMOUS.md) for exact-head automatic Squash merging and bounded unattended follow-up. Never ask the user to merge a passing PR.

Read this when running any of the six skills. Commands below run from the Git repository root. `python` means a Python 3.12+ executable; this machine's bundled Python path is recorded in the setup report. Never install a global runtime just to satisfy this spelling.

## Inputs and evidence

Requirements are supplied by the user and saved as a short local UTF-8 file. Confirm the real default branch from GitHub; `project.json` is an audited profile, not an excuse to guess a new remote. Use `git merge-base HEAD origin/main` after fetching the authorized target to freeze the comparison base. No commit/base/remote means BLOCKED: an empty repository cannot accept a first PR until its base branch exists. Never bootstrap main as an undocumented exception.

1. `python engineering/delivery.py snapshot --base <SHA> --requirements <file> --untracked-paths <json-file>` freezes the full base-to-worktree tracked diff plus explicitly selected nonignored new files. The optional JSON file is an array of approved new-file paths; omission includes no untracked files. Unrelated untracked files stay outside the candidate. All tracked staged/unstaged changes are included: if any are unrelated, stop and isolate the agreed change in a separate checkout, preserving the original work; do not test one tree and commit another. Output is local `.engineering/candidate/`. Diff/requirements can contain removed secrets: check the exact review-input files before sharing them and do not print raw scanner output.
2. `python engineering/delivery.py start --base <SHA>` creates or resumes a branch-bound local delivery ledger. It persists through commits and chat restarts. Never replace a ledger while that branch's PR remains open. For another machine recover the existing fix count and ID from the PR delivery record; if recovery is uncertain, stop rather than reset to zero.
3. Before any automatic repair batch, `python engineering/delivery.py fix --reason "..."`. This persists the reservation before edits, default max TWO across local review and CI, including abandoned attempts. Aggregate findings first; never allocate a separate budget per skill or CI run. A crash consumes its reserved batch. Only a direct user authorization can extend this delivery beyond two batches. Before editing, record the exact approval, finite new maximum and same delivery ID in its existing ledger, retaining earlier approvals and all used rounds. A request to resume after explicit disclosure of exhausted repairs and the need for additional authorization can authorize one additional consolidated batch; do not infer unlimited repairs. The default for every other delivery remains two.
4. Run the fresh read-only `code-review` and `security-review`. Store `code-review.json` and `security-review.json` beside `manifest.json`. Use `engineering/review.schema.json`: status PASS/FAIL, current `digest`, frozen `base`, `complete: true`, coverage, findings with severity/path/line/impact/fix, and reviewer identity/context. No Critical/High may remain on PASS. A process exit code alone is not a review.
5. `python engineering/delivery.py gate` rejects missing/stale/invalid evidence. `pre-delivery-check` additionally runs domain tests, TypeScript check/web build, JVM tests, Android lint and debug assembly. `lintDebug` is the variant lint task, NOT a claim of true incremental diff-only lint. Do not run connectedAndroidTest or signing/release build scripts.

Any mutation after snapshot/review requires a new snapshot and both reviews; mutation includes code generated into tracked files. Capture candidate only after intended changes settle. Evidence excludes generated assets/build trees, using .gitignore; never ignore actual source to hide findings. Check complete staged paths explicitly before commit; do not use `git add .` in this workspace.

## Preflight and cost control

Separate one-time repository/runner capability validation from feature development. Prefer GitHub connector APIs; use computer interaction only when no sufficient API exists. Use the existing repository checkout and a small scoped branch, not a repeated full-project import.

Before expensive independent review, run git diff --check, engineering/validate.py, engineering tests and tool availability checks. Settle all intended changes, snapshot and secret-screen the exact candidate, then run local checks and the two independent reviews on that frozen candidate. Reviewers receive only requirements, manifest/diff and necessary source context, never the development transcript. Consolidate all observed failures before reserving a repair batch.

Bind local command evidence to candidate base/digest. Reuse passing command results and reviews only for identical content and requirements after current_manifest/gate verification; a changed source candidate invalidates them. CI and one remote review request per new head run concurrently. A pending check is observation work, not a reason to repeat local reviews or rebuild. Keep compact state with ledger ID, head/digest, run ID, review state, blockers and next action. Never include personal data or credentials.

## Independent review

Use a subagent with `fork_turns="none"`, a minimal requirement description and the frozen diff/manifest; no author rationale, expected findings or prior verdict. Allow read-only surrounding source inspection; record reviewer context/session ID. Do not give it write tasks. A fresh `codex exec --ephemeral --sandbox read-only --output-schema ...` is a fallback only after checking local CLI help and authentication; never use resume/fork of the development conversation. Unavailable independent execution blocks Ready. Do not invoke the security-audit plugin just because ordinary delivery has a lightweight security skill.

## Publish and observe

Delivery invocation authorizes the planned feature commit/push, PR creation/update and one `@codex review` request per candidate head. Prefer available GitHub connector tools; `gh` is an optional CLI alternative and is absent on this machine at setup. Use narrow explicit file lists, preserve concurrent changes and use expected old SHA when updating a ref through connector APIs. Feature branches use `codex/<topic>`. Reject default branches, detached HEAD, unrelated remote and an uninitialized repository.

Before committing run `python engineering/delivery.py gate --staged` to compare the full index with the candidate. After a commit run `python engineering/delivery.py gate --commit HEAD` to verify its tree, including new files, modes and deletions, and ensure worktree is clean for intended scope. A connector-created remote commit must match the reviewed tree. Attach every created PR using the app artifact tool. Update an existing branch PR rather than creating duplicates. Keep a `Delivery record` in the PR body with ledger ID, branch, base/head SHA and fix-round count after every reservation/push; do not count comments as evidence of approval.

CI polling: `python engineering/delivery.py ci-wait --repo OWNER/REPO --pr N --head SHA --invocation RUN-ID` is a gh-based fallback; when using the connector implement the same deadline/semantics. Generate one invocation ID at this user-triggered delivery run's start and reuse it across all repairs/pushes; a later user-triggered run may use a new wait ID but must resume the existing repair ledger. One cumulative monotonic 480-second wait budget per invocation across all pushes, at least 30 seconds between unchanged polls, each network call bounded by remaining time. Missing checks, empty check lists, skipped/neutral/cancelled required jobs, failures to query or a different PR head are never PASS. Return PENDING with `gh pr checks N --repo OWNER/REPO` on timeout. Analyze actual failed job logs before spending a remaining fix batch. Reports from older heads are stale.

Codex PR Review is advisory until this account/repository demonstrably provides a reliable required check. Read actual authenticated reviewer output tied to the candidate SHA. PASS requires explicit completed no-finding evidence for that SHA; do not infer it from silence, emoji, comment counts, keywords or absence of findings. Record FINDINGS / PENDING / UNAVAILABLE honestly. Unresolved Critical/High or P0/P1 blocks merging. Independent local code/security review remains mandatory; native PR review unavailability cannot be disguised as PASS. In agent-verified mode, record absent GitHub enforcement and require all local and real Actions checks before API merge.

`HIGH-RISK` requires distinct fresh code and security reviewers before automatic merge and does not become PASS by having no scanner hits. Authentication, health/backup/storage, native bridge, Manifest, crypto/keys/migrations and engineering-policy/CI changes require listing exact sensitive paths. Do not expose data values or secrets in reports. Regex checks are heuristic; Gitleaks absence is disclosed and requires Codex semantic security review to complete the security report, not a user hand-review step.

## Output

Report PR URL; NORMAL/HIGH-RISK and paths; code-review PASS/FAIL; security-review PASS/FAIL; pre-delivery-check PASS/FAIL; CI PASS/FAIL/PENDING; Codex PR Review PASS/FINDINGS/PENDING/UNAVAILABLE; gate mode and whether GitHub enforces the checks; fix count; merge state MERGED/PENDING/BLOCKED; verified merged SHA; automatic follow-up status and deadline. Include evidence paths/head and limitations. Medium/Low findings remain visible without becoming mandatory blockers by default. Missing mandatory evidence blocks merging. No manual Merge recommendation or user recheck requirement.

## Release

Only explicit release invocation permits a release branch and version-change PR. Determine a semantic version from verified changes, increment Android versionCode monotonically, update versionName and package.json/package-lock.json consistently and CHANGELOG from the last verified release tag. Without a known release baseline say so. Never change package ID, vault aliases, signing identity or publish an APK. Tag creation is a separate explicit authorization and targets a verified merged release commit.
