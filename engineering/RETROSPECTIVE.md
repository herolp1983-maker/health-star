## 原因与整改

| 教训 | 固化位置 | 验证方式 |
|---|---|---|
| 首次接入、功能交付和整包导入混在一起 | DELIVERY-CHECKLIST 接入/日常分离；真实 main 起点 | control bind 核对 origin/main 与 merge-base；本次整改使用实际已合并 main，只审核新增差异 |
| 扫描器/自制适配未先验证真实消费协议 | checklist、预检模板和 compatibility_paths | 外部适配改动缺少 consumer-compatibility 证据时初始化失败；已有 NVD 时区/完整数据回归保留 |
| 每次微小修改后重复昂贵审核/构建 | control.py 阶段预留及 gate 接线 | 同一候选重复预留、过期/缺失预检和缺失阶段记录均阻断；修改后的候选不能借用旧预检 |
| 连续追加修复，未对同类故障换策略 | 默认两批原账本；失败模板与指纹记录 | 同因两次阻断后续昂贵阶段；新的通过探针和策略记录不重置预算 |
| 流程要能用于下一次交付，也要能跟随 main 前进 | 按交付 ID 保存控制记录；使用原账本的已核验基线推进链 | 跨交付隔离、真实 Git advance-base→snapshot→bind→gate 回归；原期限和历史不重置；故障探针绑定当前 base/digest |
| 长历史、原始日志和反复唤醒模型消耗 | compact state、4000字符摘要操作约束、watch.py | 无模型 API 的脚本轮询；快照状态测试覆盖静默、成功/失败/过期、陈旧/跳过/重复检查与重定向拒绝 |
| 报告与模板未更新、容易误导后续项目 | PR模板、正式自动交付报告、项目配置迁移模板 | validate.py 检查整改模板和成本策略存在且未放宽；文档交叉检查 |

脚本硬约束覆盖阶段次数、当前候选、期限、重复故障与观察状态；日志摘要长度与官方工具优先属于操作规则，不冒称能拦截模型所有工具输出。没有可信 Token 分项计量，使用可核验的阶段启动次数与时限控制成本，不承诺所有项目一次成功。
